01LedAI · Backend · Jul – Sep 2026

AI resume-editing backend

Problem

Agencies send candidates to clients on their own branded resume template. The first version generated that PDF in one LLM call, so any fix meant regenerating at full cost and losing the output.

What I built

  • Wrote the requirements analysis and HLD, then the Python/FastAPI edit and save APIs that let recruiters change an AI-generated resume by instruction or by hand.
  • Session ids HMAC-signed and bound to the user and candidate, a Redis per-session edit cap, and a small-model LLM-as-judge that screens each instruction before the main edit call.
  • On the edit call, fallback from Cerebras to AWS Bedrock with explicit per-tier timeouts and IAM-role credentials, verified by forcing the primary model to fail.

  4. →
  5. Session cap
  6. →
  7. Credit balance
  8. →
  9. Injection check
  10. →
  11. LLM judge
  12. →
  13. Edit model + fallback
  14. →
  15. Bill only if changed

Cheap checks first, money last: failed and no-op edits are never charged.

Result

What I built

How a record opens

  6. →
  7. Lazy-load neighbours

03Led · analysis, HLD, LLDFull stack · Apr – Nov 2025

Record-link custom fields

Problem

A normal custom field holds text or a fixed option. Recruiters needed Candidate and Job fields that point at real records (a company, contact, job, candidate, deal, user or team), so the value shows live details, can be filtered and exported, and never goes stale. Another team had built this for CRM records; I owned the extension.

What I built

  • No schema change: link IDs reuse the existing custom-field storage, so nothing had to be migrated.
  • No per-row requests: each list page resolves every link in one batched call into a client-side cache keyed by ID.
  • A new batch lookup API that checks the entity type against an allow-list and the user's view permission, then applies tenant and ownership filters and returns results in request order.
  • Two apps, one view: a legacy Vue 2 app and a modern Vue 3 app, co-mounted as micro-frontends, stay in sync through events. I built the AG Grid cell renderer and the sync.
  • Filters with server-side search in the shared UI kit, CSV export, inline edit, a feature flag, and exclusion from public forms.
  • A contribution to the Java search service: fixed "is not" filters silently dropping records with empty values (NULL semantics), with about 310 lines of parameterised JUnit tests across all 7 field types.

Result

8 PRs across 6 repositories; six merged within about 8 minutes in one coordinated release.

Trade-offs. Reusing the storage avoided a migration but gives up referential integrity, and its filter can't use an index; at larger scale I'd move links into a join table. I ported another team's chips and hover cards, with credit, instead of building a second set.

04Sole author of the public-forms part · HLD & LLDFull stack · Dec 2024 – Feb 2025

Conditional fields on public application forms

Problem

Public job-apply and talent-pool forms showed every candidate custom field in one flat list. Dependent fields (Country → State → City) existed only for CRM records, and a public form has no logged-in user to scope the data by.

What I built

  • Two public read endpoints that resolve the account from the job or talent-pool link and return the field-dependency tree and option lists, reusing the existing tree builder.
  • Flag-gated, parallel fetch: the page-details response already carries the account's feature flag, so the server-rendered page fetches tree and options in parallel, and only when the flag is on.
  • Index once, render as before: the client indexes the tree (root, inner, leaf). A root renders its whole subtree, child fields are skipped in the normal loop, and every other field renders exactly as it did.
  • A ~1,500-line React form engine (react-hook-form) that cascades each change per parent type (dropdown, multiselect as a union of options, checkbox), respects hidden ancestors, clears stale answers and deletes orphaned uploads once.
  • An admin settings tree with allow / required per form, where switching a parent off cascades to its descendants; plus candidate and job support in the in-app Vue 2 forms.

Result

Three PRs merged on the same day behind a flag that reverts to the flat form, with the group-testing defects resolved.

Decisions. My first version put the tree inside the page-details payload; I replaced it with dedicated endpoints so that contract stayed unchanged and the calls could run in parallel. Flag-off safety has three layers: no extra calls, a flag check on every render branch, and a fallback to the flat form if a fetch fails. I kept a static import over lazy loading to protect the page's largest contentful paint.

Multi-tenant security and rich text safe from XSS

Result

Shipped as a series of targeted fixes; I also removed static AWS keys from 7 services in an org-wide change. In the rich-text analysis I asked how many existing records already broke the new limit: 12,449 did, so Product applied it to new input only.
